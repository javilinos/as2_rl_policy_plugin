# as2_rl_policy

An Aerostack2 motion-controller plugin (`plugin_name: rl_policy`) that flies quadlab's exported
rates policies: a race policy for N laps, then a hover policy that holds where the race ended
(`mission: race`), or the hover policy alone at a setpoint (`mission: hover`). It takes
TRAJECTORY (yaw angle) and gives BODY_RATES: collective thrust (N) and body rates (rad/s), one
policy step per controller tick.

- `as2_rl_policy_core`: the policy file loader (`quadlab_policy` v1, goldens checked on load),
  the gate-relative observation, the gate sequencer, the action decode and the mission
  (Idle, Race, Hold). No ROS.
- `as2_rl_policy_lib`: the `ControllerBase` plugin around it.

Every race exit (laps done, a missed gate, no pass within the timeout, out of bounds, a HOVER
mode request) ends in a hold at the current pose with the `hover` policy, or, for laps done with
`hold.after_race: setpoint`, at `hold.setpoint`, and with `hold.after_race: end_point` at the end
point of the course the race pilot sent (below). Landing stays manual.

Each policy file names its observation layout (`observation.layout`), and each phase builds the
active policy's: `gate_relative_20`, the kernel's 20 entries with its Euler roll, pitch and yaw to
the gate at 6..8, or `gate_relative_r6_23`, the same row with those three angles replaced by the
six R6 entries at 6..11 (`[R00, R10, R20, R02, R12, R22]` of `Rz(yaw) Ry(pitch) Rx(roll)`, the
body x and thrust axes in the gate frame, quadlab's `rates_wrapper.attitude: r6`), continuous
where the angles wrap. Either is followed by `observation.action_history` commands, so a race
policy in one layout hands over to a hover policy in the other.

## Parameters

`config/rl_policy_default.yaml` carries every required key with its default; the flight's own
file (generated by quadlab's `gen_controller`) overrides it. Eight keys are optional and not in
it: `course.gates_shape` (per gate, the opening's geometry: 0 a square, 1 an octagon; all squares
when absent), `course.gates_virtual` (per gate, true where nothing stands to hit; none when
absent), `course.gates_pass_tolerance_m` (per gate, its own pass window; its shape's when
absent), `race.octagon_pass_tolerance_m` and `race.octagon_valid_half_m` (the square's values
when absent), `race.virtual_valid_half_m` (a virtual gate's valid window; its shape's when
absent) and `race.stop_latency_s` and `race.stop_decel_ms2` (the stop check, off when both are
absent or zero). Integers are `config_version`, `race.laps`, `race.exit_debounce_steps` and the
entries of `course.gates_shape`, booleans the entries of `course.gates_virtual`; every other
number is a double and must be written with a decimal point. The plugin refuses to fly on a
missing or mistyped key, a policy whose goldens do not reproduce, `cmd_freq` other than `1 / dt`,
or pose/twist frames other than `/earth`, and says why at FATAL level. It also refuses the keys
it no longer reads: a `course.gates_shape` entry 2 (a virtual gate is now
`course.gates_virtual`) and `race.virtual_half_m` (the pass window is the shape's, the training
window `race.virtual_valid_half_m`).

A gate is a pose in the course list, and a crossing of its plane is judged the same way whether a
gate stands there or not: it passes iff its norm in the gate's shape is below that shape's pass
window, `max(|u|, |v|) < race.pass_tolerance_m` for a square and
`max(|u|, |v|, (|u| + |v|) / sqrt(2)) < race.octagon_pass_tolerance_m` for an octagon. quadlab
writes both as the gates' real half-openings. `course.gates_pass_tolerance_m`, one entry per gate
of `course.gates_*`, replaces each gate's shape window with its own, in the same norm: quadlab
gives a powerloop's top the whole frame its network trained on. What differs is a crossing outside the window: at a
physical gate it is a miss and the race exits to the hold; at a virtual gate
(`course.gates_virtual`) there is nothing to hit, so it is neither a pass nor a miss. The target
stays and the race goes on, so the vehicle has to come round again; the crossing is logged and
reported as the last one (`last_crossing_passed: false`), and `race.gate_timeout_s` keeps running.

The valid windows, `race.valid_half_m`, `race.octagon_valid_half_m` and
`race.virtual_valid_half_m` (the windows the policy was trained to pass, tighter than the gates),
are logged with each crossing (`valid` or `outside the valid opening`, `last_crossing_valid`) and
never decide a pass.

The race's room check reads the position alone unless the stop check is on. Then a step is also
outside when its predicted stop, `p + v * race.stop_latency_s + v |v| / (2 *
race.stop_decel_ms2)` from the state's position and world velocity (the last term left out when
the deceleration is zero), is outside the bounds plus `race.bounds_margin_m` in x or y or above
`race.ceiling_m`. The exit is the same (`out_of_bounds` after `race.exit_debounce_steps` outside
steps in a row, a hold where the vehicle is); its log says which test was outside and gives both
points, and the status carries `predicted_stop_x/y/z`. quadlab's `gen_controller` writes the
valid windows and the stop check from the race policy's frozen env, and the pass windows from the
track's gate geometry.

`policies.files` may be relative: the controller process resolves them against its working
directory, which is the directory `ros2 launch` was started from, and logs the absolute path.

The rotor speeds come from `motor_speed.topic`, a `sensor_msgs/JointState` with `velocity` in
rad/s in the policy's motor order (RR, FR, RL, FL). The default is the aircraft's
`sensor_measurements/motor_angular_speed` (as2_platform_indiflight); quadlab's generated file
names the simulator's `sensor_measurements/motor_speed`.

Debug topics: `debug/controller/rl_policy/status` (`diagnostic_msgs/DiagnosticStatus`) and
`debug/controller/rl_policy/step` (`std_msgs/Float64MultiArray`, 64 columns labelled
`rl_policy_step_v2`: time, phase, target, lap, the target frame, the state, 31 observation
columns, NaN past a shorter observation, the action and the command), under the drone namespace.
The status carries `hold_reference`,
`setpoint_source` (`configured`, `sent`, `here` for a pose the vehicle was at, `end_point` for
the race pilot's end point, `none`) and
`setpoint_x/y/z/yaw`, which the hover mission reports from Idle on: where its hold will start.
The last crossing is `last_crossing_gate`, `_lateral_m`, `_vertical_m`, `_passed`, `_valid` and
`_virtual`, beside the square windows `pass_tolerance_m` and `valid_half_m`.

## Gate offset

A detector that sees part of a gate's opening blocked can move the gate's middle point for the
race policy: `gate_offset.topic` (default `rl_policy/gate_offset`, under the drone namespace; empty
turns it off) carries a `geometry_msgs/Vector3Stamped` whose `vector` is the offset in the gate's
own axes, [through, left, up] in m, for gate `gate_offset.gate` of the lap (default 0, the first
gate). While a message is at most `gate_offset.timeout_s` old (default 0.1 s, five periods of a
50 Hz detector), the race's observation sees that gate moved: its position entries as the target,
and the next-gate entries that name it. The sequencer still judges the gate where it stands, in
its own window, and a hold ignores the offset. The step topic's target frame is the moved gate,
so a recorded flight carries each applied offset; the status carries `gate_offset_applied`,
`gate_offset_through/left/up` and `gate_offset_age_s`. The policies never trained on a moved
gate: this is a test of how they take one.

## Hold reference

The hover mission holds `hold.setpoint` until a reference is sent. With
`hold.reference: sent_or_configured` (the default) the hold setpoint is the LAST point of the
latest `as2_msgs/TrajectorySetpoints` on `motion_reference/trajectory`, its position and
`yaw_angle`, clamped like `hold.setpoint` (x and y into the course bounds, z no lower than
`hold.min_altitude_m`). A course sent before the pilot engages is where the hold starts; one
sent during the hold moves the setpoint, and the hover policy carries on with its history. A
republish of the same course (as2_race_pilot sends it every 100 ms) changes nothing. The frame
must be `earth`, `/earth` or empty: other frames and non-finite points are ignored with a
warning, empty courses are ignored, and the setpoint stays. A mode set keeps the reference.

`hold.reference: configured` ignores sent references; so does the race mission, and a HOVER
request holds where it was made. The controller manager passes references on only once a
control mode is set, so the course has to arrive (or keep arriving) after `set_control_mode`.

## Course from the race pilot

With `course.source: race_pilot` the race mission flies the course as2_race_pilot sends on
`motion_reference/trajectory`, the message the MPCC flies, instead of `course.gates_*`. It reads
the crossings alone: the points whose id carries the `_gp` mark, each a gate at its `position`
crossed along its `yaw_angle`. The gate's name is the id without its marks (`_gp _ny _rt _ls _sy
_vn`) and lap tag (`_lap2`); it is virtual when it contains `_v` and an octagon when it ends in
`_oct`, as the rest of the stack names them. Everything else the MPCC is told, pass-through
points and heading and speed marks, is ignored, and so is the end point (the last point, id
`end`) unless `hold.after_race` is `end_point`. The crossings repeat with one
lap's period, and the race finishes on the LAST crossing sent: a closed circuit's closing first
gate is raced (2 laps of 4 and gate01, 9 passes).

Before the race can start, one lap must match `course.gates_*`, the circuit the race policy
trained on, gate by gate: the same count and order, positions within `course.match_position_m`,
yaw within `course.match_yaw_deg`, the same virtual flag and shape. A course that does not match
is refused at ERROR level with the first gate that differs, and no command is computed until one
that matches arrives; the status says `course: refused: ...`. One that matches is raced with the
sent gates' poses and the configured gates' own pass windows (`course.gates_pass_tolerance_m`,
gate by gate as matched) (`course: matched`, `course_crossings`). A republish changes nothing, and
a different course once the race has started is ignored with a warning.

`hold.after_race: end_point` holds the finish at the sent course's end point, the position the
pilot gives the track's `end_point`, at `hold.setpoint`'s yaw (the end point carries none), and
reports it as `setpoint_source: end_point`. A course without an end point holds at
`hold.setpoint` (`configured`), with a warning when it is matched; so `hold.setpoint` must lie
inside the bounds, and quadlab writes it at the circuit's end point with the yaw for the camera.
Only the race mission on `course.source: race_pilot` takes it.

A policy file may carry the circuit it trained on, a `course` block of one lap of crossings
(`{name, position, yaw, virtual, shape}`). A race policy that does refuses any `course.gates_*`
but its own, whatever the source.

## Run

The launch file layers the node's parameters, each over the one before: as2_motion_controller's
defaults, `config/rl_policy_default.yaml`, `plugin_config_file` (the `rl_policy` block), then
`config_file` (a node file with a `controller_manager` block, or a whole flight under `/**`),
then `plugin_name`, `use_bypass: false`, the available modes and `use_sim_time`. Either file
may be left out, not both. `use_sim_time` is false unless given.

On the aircraft only the safety pilot arms and switches to offboard, and the controller manager
runs the plugin only while `platform/info` reports both: the pilot's offboard switch starts the
mission.

```bash
ros2 launch as2_rl_policy rl_policy.launch.py namespace:=drone0 \
    config_file:=config/config.yaml plugin_config_file:=config/rl_policy.yaml
ros2 run as2_rl_policy engage.py --namespace drone0    # TRAJECTORY mode, then wait for the pilot
```

`engage.py` waits for the controller's service, sets TRAJECTORY (yaw angle) with retries, then
waits for `platform/info` to report armed, then offboard, logs each and exits 0; `--timeout S`
gives up after S seconds, and it never calls the arming or offboard services. as2_race_pilot
does the same and sends its course besides, which the hover mission then holds at its end.

In simulation, where the platform takes the arming and offboard services, `--arm` requests
them after the mode:

```bash
ros2 launch as2_rl_policy rl_policy.launch.py namespace:=drone0 use_sim_time:=true \
    config_file:=<params.yaml>
ros2 run as2_rl_policy engage.py --namespace drone0 --arm
ros2 service call /drone0/controller/set_control_mode as2_msgs/srv/SetControlMode \
    "{control_mode: {control_mode: 1, yaw_mode: 1}}"   # HOVER: hold where it is
```

## Build and test

```bash
colcon build --symlink-install --packages-select as2_rl_policy --cmake-args -DCMAKE_BUILD_TYPE=Release
colcon test --packages-select as2_rl_policy && colcon test-result --verbose
```

The test fixtures in `tests/fixtures/` are written by quadlab:
`python3 -m quadlab.cli.gen_plugin_fixtures --out <this package>/tests/fixtures`.
